## Velora OS v0.12.0
### Что нового
- Образ для флешки `velora-usb.img` (64 МиБ): GPT и раздел EFI FAT32 с загрузчиком, ядром и initramfs. Собирается вместе с ISO утилитой `tools/mkusb` и выкладывается в релиз с контрольной суммой. Инструкция по записи и загрузке на реальном компьютере — `docs/hardware.md` (решение D41).
- Таймеры: TSC и таймер APIC калибруются по HPET, при его отсутствии — по таймеру ACPI PM, и только в последнюю очередь по PIT. Без PIT система больше не останавливается. Журнал загрузки сообщает источник калибровки и инвариантен ли TSC (D40).
- Журнал паники на диске: при панике или фатальном исключении ядро записывает отчёт и последние сообщения в `velora-panic.log` на разделе EFI Velora (или на любом томе FAT, где этот файл создан заранее). При следующей загрузке журнал переносится в `velora-panic.prev.log` и выводится предупреждение (D39).
- Журнал ядра: последние 64 КиБ сообщений доступны через `/dev/kmsg`, команда `dmesg`.
- Консоль: на экранах шириной от 2560 точек шрифт увеличивается вдвое; параметр ядра `velora.fontscale=1..4`.
- `velora-fsck --cat ПУТЬ` выводит файл из образа диска (так тесты читают журнал паники).
- Тесты: новый тест `qemu_run.py usb` загружает `velora-usb.img` как USB-накопитель на контроллере xHCI без CD и без HPET, проверяет калибровку по таймеру ACPI PM, вход и `dmesg`. Тесты ядра сравнивают частоту TSC по HPET, таймеру ACPI PM и PIT, проверяют масштаб шрифта, инверсию и курсор. После каждой загрузки ktest хост читает журнал паники с тестового диска, вторая загрузка находит журнал первой. 176 юнит-тестов на хосте, 92 теста ядра.

- Нет.

### Известные проблемы
- С флешки журнал паники не пишется: USB появится на этапе 15. Пишется на раздел EFI установленной системы (SATA, NVMe, virtio).
- Если паника случилась посреди запроса к тому же диску, запись журнала может не удаться (выводится сообщение).
- `/dev/kmsg` лучше читать одним вызовом (так делает `dmesg`): вывод журнала на консоль сам попадает в журнал.
- Используется одно ядро процессора; клавиатура только PS/2; сеть только virtio-net (этапы 14–16).
- Ограничения прошлых версий остаются (сигналов нет, одна блокировка VFS, только UEFI, нет DNS, virtio-blk не работает с QEMU 8.2 — #19).

### What's new
- A USB drive image, `velora-usb.img` (64 MiB): a GPT and a FAT32 EFI partition with the bootloader, the kernel and the initramfs. It is built together with the ISO by `tools/mkusb` and published in releases with a checksum. How to write it and boot a real computer: `docs/hardware.md` (decision D41).
- Timers: the TSC and the APIC timer are calibrated against the HPET, without one against the ACPI PM timer, and only as a last resort against the PIT. The system no longer stops without a PIT. The boot log names the calibration source and whether the TSC is invariant (D40).
- Panic log on disk: on a panic or a fatal exception the kernel writes the report and the latest messages to `velora-panic.log` on the Velora EFI partition (or any FAT volume where the file was created beforehand). At the next boot the log moves to `velora-panic.prev.log` and a warning is printed (D39).
- Kernel log: the last 64 KiB of messages are available through `/dev/kmsg`, command `dmesg`.
- Console: the font is doubled on screens at least 2560 pixels wide; kernel parameter `velora.fontscale=1..4`.
- `velora-fsck --cat PATH` prints a file from a disk image (the tests read the panic log this way).
- Tests: a new `qemu_run.py usb` test boots `velora-usb.img` as a USB drive on an xHCI controller, with no CD and no HPET, and checks calibration against the ACPI PM timer, login and `dmesg`. Kernel tests compare the TSC rate measured against the HPET, the ACPI PM timer and the PIT, and check the font scale, reverse video and the cursor. After each ktest boot the host reads the panic log from the test disk, and the second boot finds the first one's log. 176 host unit tests, 92 kernel tests.

### Known issues
- No panic log when running from a USB drive: USB support comes in stage 15. The log is written to the EFI partition of an installed system (SATA, NVMe, virtio).
- If the panic interrupted a request on the same disk, writing the log may fail (a message says so).
- `/dev/kmsg` is best read in one call (as `dmesg` does): printing the log on the console adds to the log.
- One CPU core is used; PS/2 keyboard only; virtio-net only (stages 14–16).
- Earlier limitations remain (no signals, one VFS lock, UEFI only, no DNS, virtio-blk does not work with QEMU 8.2 — #19).
